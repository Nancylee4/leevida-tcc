1. Introdução

O LeeVida é um sistema web de prontuário clínico concebido para pequenas clínicas angolanas, com a Clínica EmiPharma (Caála, Huambo) como caso de estudo. Este manual destina-se a programadores e técnicos de informática que precisem de instalar o sistema, corrigir erros, acrescentar funcionalidades ou colocá-lo em produção. Pressupõe familiaridade com TypeScript, Node.js, React e bases de dados relacionais.

O código está organizado como um monorepo com dois projectos independentes:

PastaConteúdo
leevida-backend/API REST em NestJS, com Prisma (ORM) e PostgreSQL.
leevida-front-end/Aplicação web (Single Page Application) em React, Vite e Tailwind CSS.
Convenções deste manualOs caminhos de ficheiros são relativos à raiz do monorepo. Os comandos de terminal são escritos para bash (Git Bash no Windows). As rotas da API omitem o prefixo /api/v1, salvo indicação em contrário.

2. Visão geral do sistema

O sistema serve quatro perfis de utilizador, cada um com um conjunto fechado de permissões aplicado no servidor:

PerfilO que faz no sistema
AdministradorGere as contas dos profissionais, repõe senhas, desactiva contas, consulta o registo de auditoria e vê os indicadores globais.
EnfermeiroRegista pacientes (o registo cria também a conta do paciente), faz a triagem com sinais vitais, sintomas e prioridade de Manchester, e acompanha o estado dos exames sem ver os resultados.
MédicoGere a agenda, aceita ou rejeita consultas, atende a fila por prioridade, regista diagnósticos e códigos CID-10, emite e assina prescrições, solicita exames e regista resultados, emite justificativos e usa o assistente de IA.
PacienteNão se auto-regista: entra com as credenciais dadas pelo enfermeiro. No portal marca consultas e consulta o seu histórico, receitas e exames.

Às funcionalidades clínicas juntam-se notificações em tempo real, exportação para Excel e PDF, registo de auditoria de todas as acções críticas e seis funcionalidades de inteligência artificial de apoio à decisão (secção 10).

3. Arquitectura

O LeeVida segue uma arquitectura cliente-servidor em três camadas. O navegador comunica apenas com a API, nunca directamente com a base de dados nem com o serviço de IA.

CamadaResponsabilidade
ApresentaçãoSPA em React: páginas por perfil, componentes reutilizáveis e contextos de estado (autenticação, notificações, tema e mensagens). Fala com a API por um cliente HTTP único, que injecta o token JWT e renova a sessão automaticamente.
NegócioAPI NestJS organizada em módulos por domínio. Concentra validação, autenticação, autorização por perfil, regras de negócio, auditoria, notificações (Server-Sent Events) e a integração com a IA.
DadosPostgreSQL, acedido exclusivamente pelo PrismaModule. O esquema e as migrações estão em leevida-backend/prisma/.
Serviço externoGoogle Gemini API, chamada apenas pelo AiModule, com dados anonimizados. É opcional: sem chave, o sistema funciona com regras locais.

6. Preparar o ambiente de desenvolvimento

6.1 Pré-requisitos

  • Node.js 20+ e npm.
  • PostgreSQL 16+ instalado localmente, ou Docker Desktop (o projecto inclui um docker-compose.yml).
  • Git.
  • Opcional: uma chave da API Gemini (aistudio.google.com/apikey) para activar a IA.

6.2 Base de dados

Com Docker, a partir de leevida-backend/:

docker compose up -d     # PostgreSQL 16 na porta 5433, base leevida_db

Com PostgreSQL nativo, basta criar uma base e apontar DATABASE_URL para ela.

Copiar leevida-backend/.env.example para .env e preencher:

7.2 Ciclo de vida de um pedido

  1. Middleware (main.ts): Helmet (cabeçalhos de segurança), cookie-parser, contexto do pedido, compressão (excepto SSE) e CORS restrito a CORS_ORIGIN.
  2. Guards globais, por esta ordem: ThrottlerGuard (100 pedidos/min por omissão), JwtAuthGuard (exige token, salvo rotas com @Public()) e RolesGuard (compara o perfil do utilizador com @Roles(...)).
  3. ValidationPipe global: valida o DTO, rejeita campos desconhecidos (whitelist + forbidNonWhitelisted) e converte tipos.
  4. Controller → Service: o serviço aplica as regras de negócio, usa o Prisma, regista a auditoria e emite notificações.
  5. Resposta: o LoggingInterceptor regista o pedido e o HttpExceptionFilter uniformiza os erros.

Todas as rotas ficam sob /api/v1 (prefixo global e versionamento por URI). A documentação interactiva Swagger está em /api/docs.

7.3 Autenticação e autorização

  • Login (POST /auth/login): valida e-mail e senha (bcrypt) e devolve um access token (15 min) no corpo. Guarda um refresh token (7 dias) num cookie httpOnly, inacessível a JavaScript.
  • Renovação (POST /auth/refresh): o refresh token é rodado a cada uso, e a base de dados guarda apenas o seu hash (User.hashedRefreshToken). O frontend chama-o automaticamente quando recebe 401 e quando a página é recarregada.
  • Senhas provisórias: contas criadas pelo administrador ou pelo enfermeiro, e senhas repostas, recebem uma senha gerada sem caracteres ambíguos e mustChangePassword = true. O utilizador tem de a trocar no primeiro login.
  • Política de senhas (common/password-policy.ts): mínimo de 8 caracteres, com pelo menos uma letra e um número.
  • Decorators: @Public() dispensa autenticação; @Roles(Role.MEDICO, …) restringe por perfil (ao nível da classe ou do método); @CurrentUser() injecta o utilizador autenticado.
  • Contas desactivadas (deactivatedAt) não conseguem autenticar-se. As contas nunca são apagadas, para preservar a autoria clínica e a auditoria.

7.4 Regras de negócio principais

  • Só enfermeiro e administrador registam pacientes. O registo cria a conta do paciente; o paciente nunca se auto-regista.
  • Só médico e administrador criam consultas normais e de retorno. A triagem (enfermeiro) cria a consulta em estado AGUARDANDO.
  • Transições de estado da consulta: AGENDADA → aceitar (atribui o médico) ou rejeitar (CANCELADA); AGENDADA/AGUARDANDO → iniciar (EM_ANDAMENTO) → concluir (CONCLUIDA). A API recusa transições inválidas.
  • A fila de espera do médico ordena por prioridade de triagem (vermelho → azul) e depois por hora de chegada.
  • O paciente só pode marcar com médicos que tenham agenda activa na especialidade escolhida, dentro do horário definido (validado no fuso CLINIC_TIMEZONE).
  • Só o médico que emitiu uma receita a pode assinar.
  • O enfermeiro nunca vê resultados de exames: a listagem remove result, resultDate e a análise da IA quando o pedido vem de um ENFERMEIRO. Só médico e administrador registam resultados.
  • Um justificativo médico só pode ser emitido a partir de uma consulta EM_ANDAMENTO ou CONCLUIDA.
  • Os pacientes não se apagam: são arquivados (archivedAt) e saem das listagens.

7.5 Notificações em tempo real

O NotificationsService grava cada notificação na tabela notifications e envia-a pelo canal Server-Sent Events GET /notifications/stream. As notificações podem ser dirigidas a um utilizador (notifyUser) ou a um perfil inteiro (notifyRole, por exemplo "novo paciente em triagem" para todos os médicos). O NotificationContext do frontend mantém a ligação aberta e actualiza o sino da barra superior.

Limitação conhecidaAs ligações SSE vivem na memória do processo. Com mais do que uma instância da API (escalonamento horizontal), é preciso um canal partilhado, como Redis pub/sub.

7.6 Auditoria

O AuditLogsService.log(actor, acção, recurso, id) grava o utilizador, o nome, a acção, o recurso, o identificador, a data/hora e o IP. É chamado pelos serviços em todas as acções críticas: autenticação, consultas, receitas, exames, consultas ao prontuário, gestão de utilizadores, exportações e cada utilização da IA. Exemplos de acções: LOGIN, CONSULTOU_PRONTUARIO, ACEITOU_CONSULTA, FEZ_UPLOAD_RECEITA, ASSINOU_RECEITA_COM_ALERTA_IA, IA_SUGERIU_PRIORIDADE. A tabela usa onDelete: Restrict sobre o utilizador, por isso os registos não se perdem.

10. Módulo de inteligência artificial

O AiModule implementa seis funcionalidades de apoio à decisão clínica com modelos Google Gemini: triagem, resumo pré-consulta, assistente de prescrição, verificação da receita, interpretação de exames e sugestão de CID-10. Princípio central: a IA sugere, o profissional decide, e regras determinísticas locais funcionam mesmo sem IA.

10.1 Componentes

FicheiroResponsabilidade
ai.controller.tsEndpoints /ai/*, perfis e limite de 20 pedidos/min.
ai.service.tsAs seis funcionalidades: combina regras e IA, grava os resultados e regista a auditoria.
gemini.client.tsComunicação com a API Gemini: cadeia de modelos de reserva, timeout de 25 s por modelo, pausa de 3 min de modelos que falham, respostas JSON com esquema.
clinical-context.tsConstrói o contexto clínico anonimizado: idade, sexo, grupo sanguíneo, alergias, sinais vitais, diagnósticos, medicação e exames recentes.
clinical-rules.tsRegras determinísticas: prioridade mínima por sinais vitais (triageFloor), conflitos de alergia por classe de fármaco (allergyConflicts) e valores laboratoriais de pânico.

10.2 Regras clínicas (resumo)

  • Triagem: a prioridade final é sempre a mais urgente entre a da IA e a calculada pelos sinais vitais (por exemplo, SpO₂ < 90% impõe no mínimo laranja). A IA pode subir a prioridade, nunca descê-la.
  • Alergias: cruzamento por classes (penicilinas, AINE/aspirina, sulfonamidas, …), sem falsos positivos por semelhança de nome (por exemplo, "ácido fólico" não é confundido com "ácido acetilsalicílico").
  • Valores de pânico: hemoglobina, plaquetas, leucócitos, potássio, sódio, glicemia e cálcio, com vírgula decimal, separadores de milhares e conversão de unidades. Prevalecem sobre a IA.

Os limiares estão todos em clinical-rules.ts para facilitar a revisão pela direcção clínica antes do uso em produção.

10.3 Fiabilidade

  • Cadeia de modelos configurável (GEMINI_MODEL e GEMINI_FALLBACK_MODELS); um modelo que falha (sobrecarga, limite ou timeout) fica em pausa 3 minutos e passa para o fim da fila.
  • Análise de exames em segundo plano, com novas tentativas após 30 s, 2 min e 5 min.
  • Degradação graciosa: sem IA, a triagem usa as regras, a verificação cruza as alergias e o assistente mostra uma mensagem clara.
  • Cache do resumo pré-consulta até 6 horas, invalidada quando o prontuário muda.
  • Envio apenas das 20 últimas mensagens da conversa do assistente.

10.4 Privacidade

O modelo nunca recebe nome, BI, telefone, e-mail, morada, contacto de emergência, dados do médico ou credenciais. Um teste automático garante que o contexto enviado contém as alergias mas não estes dados. A chave existe apenas no servidor.

Antes de usar com dados reaisNo plano gratuito da API Gemini, a Google pode usar o conteúdo dos pedidos para melhorar os seus produtos. Para dados de pacientes é obrigatório activar a facturação (plano pago) no projecto Google Cloud e garantir que o consentimento informado cobre o uso de IA.

11.3 Cliente da API

services/apiClient.ts centraliza os pedidos: junta o access token (guardado só em memória), envia o cookie (credentials: 'include'), tenta uma renovação automática ao receber 401 e repete o pedido, e converte erros em ApiError. Cada recurso tem o seu módulo em services/api/, com funções tipadas.

11.4 Exportações e impressão

O ExportMenu gera ficheiros Excel (ExcelJS) e PDF (jsPDF + autoTable) no próprio navegador, a partir das colunas definidas em utils/exportColumns.ts, e regista cada exportação na auditoria. utils/printDocuments.ts produz receitas e justificativos para impressão e assinatura.

11.5 Componentes de IA

AiAssistant (painel flutuante do médico), AiPatientSummary (resumo na ficha), PrescriptionSafetyModal (verificação antes de assinar), ExamInsightModal (interpretação) e TriageBadge (cor de Manchester). Todos identificam visualmente o conteúdo gerado por IA e lembram que a decisão é clínica.

14. Implantação em produção

  1. Servidor: Linux (ou Windows Server) com 2 vCPU, 4 GB de RAM e 40 GB SSD, local na clínica ou alugado na nuvem. Instalar Node.js 20+, PostgreSQL 16+ e um proxy reverso (Nginx ou Caddy).
  2. Base de dados: criar utilizador e base próprios, sem acesso pela rede externa.
  3. API: npm ci, npx prisma migrate deploy, npm run build e executar node dist/main com um gestor de processos (systemd ou PM2). Definir NODE_ENV=production, segredos JWT novos, CORS_ORIGIN com o domínio real e TRUST_PROXY=1.
  4. Frontend: VITE_API_URL=https://dominio/api/v1 npm run build e servir a pasta dist/ pelo proxy, com fallback para index.html.
  5. HTTPS: certificado TLS (por exemplo, Let's Encrypt) no proxy. Desactivar a compressão para o caminho SSE /api/v1/notifications/stream, ou garantir que o proxy não faz buffering.
  6. Não correr o seed em produção. Criar o primeiro administrador manualmente e desactivar as contas de demonstração.
  7. Cópias de segurança: pg_dump diário, cifrado e guardado fora do servidor, com teste periódico de reposição.
  8. IA: activar a facturação da API Gemini e configurar GEMINI_API_KEY.
Itens pendentes conhecidosPaginação nas listagens, fotos de perfil em armazenamento de ficheiros (hoje em base64 na base de dados), Redis para notificações com várias instâncias, sessão única por utilizador, monitorização de erros, testes ponta a ponta no navegador e recuperação de senha por e-mail (exige SMTP). Para produção, convém também ocultar o Swagger.

15. Guias práticos de evolução

15.1 Acrescentar um campo à base de dados

  1. Editar o modelo em prisma/schema.prisma.
  2. npx prisma migrate dev --name descricao_curta: gera a migração e actualiza o cliente.
  3. Acrescentar o campo ao DTO (com validações class-validator) e ao serviço.
  4. Acrescentar o campo ao tipo em leevida-front-end/src/types e ao formulário ou listagem.
  5. Se o campo for exportável, acrescentá-lo a utils/exportColumns.ts.

15.2 Acrescentar um endpoint

// exams.controller.ts
@Roles(Role.MEDICO, Role.ADMIN)
@Patch(':id/cancel')
cancel(@Param('id') id: string, @CurrentUser() user: RequestUser) {
  return this.examsService.cancel(id, user);
}

// exams.service.ts
async cancel(id: string, actor: RequestUser) {
  const exam = await this.findById(id);              // lança 404 se não existir
  if (exam.status === 'CONCLUIDO') throw new ForbiddenException('Exame já concluído');
  const updated = await this.prisma.exam.update({ where: { id }, data: { status: 'CANCELADO' } });
  await this.auditLogsService.log(actor, 'CANCELOU_EXAME', 'exam', id);
  return updated;
}

O exemplo é ilustrativo: o estado CANCELADO exigiria acrescentá-lo primeiro à enumeração ExamStatus (guia 15.1). Depois, acrescentar a função em services/api/exams.ts no frontend e um teste no *.service.spec.ts.

15.3 Acrescentar uma página

  1. Criar src/pages/NovaPage.tsx.
  2. Registar a rota em App.tsx dentro de DashboardLayout, com <ProtectedRoute roles={[...]}>.
  3. Acrescentar a entrada no menu em layouts/Sidebar.tsx para os perfis certos.

15.4 Ajustar regras clínicas

Alterar os limiares em src/ai/clinical-rules.ts e actualizar os testes em ai.service.spec.ts. Qualquer alteração deve ser validada pela direcção clínica.

16. Resolução de problemas

SintomaCausa provável e solução
EADDRINUSE :3000 ao arrancar a APIOutra aplicação usa a porta. Usar PORT=3001 e ajustar VITE_API_URL e CORS_ORIGIN.
Erros de CORS no navegadorO Vite mudou para outra porta (5174) porque a 5173 estava ocupada. Arrancar com npx vite --strictPort ou alinhar CORS_ORIGIN.
